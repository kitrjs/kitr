# Working in a kitr project

kitr fixes the conventions and writes them down. Every kind of file has one home, every command runs from flags, and the CLI reports in JSON. Follow the steps below instead of guessing.

## 1. Read the project first

- Read `AGENTS.md`. `kitr new` wrote it and every `kitr add` keeps its `## kitr: <name>` sections current. Those rules beat your defaults.
- Read `kitrrc.ts`. It lists every package, provider and platform the app loads. Options live in `config/<package>.ts`.
- Run `kitr info` for a JSON summary: kitr version, package manager, `serverOnly`, platforms, packages, providers, directories.

Run the CLI through the project's package manager (`pnpm kitr ...`, `npx @kitr/kitr ...`) so the project's own version answers.

## 2. Create files with `kitr make`

Never create a file by hand when a generator exists for its kind.

```sh
kitr make --json                      # every generator, its owner and the path it writes
kitr make:page projects               # app/pages/projects.tsx and a .page() line in app/routes.ts
kitr make:controller projects --resource
kitr make:query projects/list --dry-run   # print what would be written, change nothing
```

- A nested name makes a feature folder: `kitr make:controller admin/users` writes `server/controllers/admin/users-controller.ts`.
- File names come out kebab-case whatever you type.
- `kitr make:controller` prints the route line for `server/routes.ts`. Add it.
- Packages add generators when they are added: `make:job` exists after `kitr add jobs`, `make:channel` after `kitr add realtime`. Check `kitr make --json`, not memory.

## 3. Add packages and platforms with `kitr add`

```sh
kitr add auth --help        # the package's questions, each as a flag
kitr add jobs --no-worker   # answer a question with its flag
kitr add forms --yes        # take every default
kitr add mail --dry-run     # preview the changes
kitr add web site           # add a platform: web, server, desktop, tauri, mobile
kitr remove mail            # reverse of add; lists files that still import it
```

`kitr add` installs the package and what it requires, registers its provider in `kitrrc.ts`, writes `config/<pkg>.ts` and adds its rules to `AGENTS.md`. Do not do these steps by hand. Re-read `AGENTS.md` after adding a package.

## 4. Code rules

- Import framework code from the `@kitr/*` package, never from the upstream library it re-exports: `@kitr/query`, not `@tanstack/react-query`; `@kitr/router`, not `@tanstack/react-router`. `kitr doctor` flags direct upstream imports.
- Mutations declare cache `effects`. Do not call `queryClient.invalidateQueries` in a component.
- `server/` never imports React. A declaration both sides read (a zod schema, an error class, a channel) lives in `app/`.
- A file carries a kind suffix exactly when its export does: `UsersController` in `users-controller.ts`, `BillingService` in `billing-service.ts`. `define*()` files have none: `server/jobs/send-receipt.ts`.
- Pages are named by their URL path: `/projects/$id` is `app/pages/projects/id.tsx`.
- Import across folders with `#app/*`, `#components/*`, `#server/*`, `#config/*`, `#kitr/*`. Use relative imports only inside one folder.
- Do not edit `.kitr/`. It is generated by `kitr types`.

## 5. Where things live

| Path | What goes there |
| --- | --- |
| `kitrrc.ts` | Packages, providers and platforms |
| `config/<package>.ts` | One options file per package |
| `app/routes.ts` | The page table: every `.page()` and `.layout()` |
| `app/pages/`, `app/layouts/` | Route components, named by URL path |
| `app/components/` | Reusable UI; `ui/` is copied by `kitr ui add`, `forms/` holds forms |
| `app/queries/`, `app/actions/<feature>/` | Data the app reads and writes |
| `app/validators/` | zod schemas shared by forms, actions and controllers |
| `app/exceptions/`, `app/channels/`, `app/providers/` | Errors, realtime channels, lifecycle providers |
| `server/routes.ts` | API endpoints and sockets |
| `server/controllers/`, `services/`, `middleware/`, `jobs/`, `mail/` | Server code, never React |
| `test/` | App-level tests (`kitr make:test <name>`) |
| `.kitr/` | Generated types, read through `#kitr/*` |

`kitr make` in the project is the source of truth for the kinds it has.

## 6. Check your work

Run these after every change, and before you say you are done:

```sh
kitr types                 # regenerate .kitr/
kitr doctor --json         # findings with level, message and fix; exit code 1 on errors
```

Then run the project's own `typecheck` and `test` scripts from `package.json`. Treat any doctor finding with `"level": "error"` as a failure and fix it. Use the `fix` field when it is there.
